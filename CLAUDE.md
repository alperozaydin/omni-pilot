# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Omni Pilot is a Python CLI that analyzes daily micronutrient intake from MacroFactor nutrition-tracking `.xlsx` exports. It compares intake against configurable NIH/WHO reference ranges and produces terminal + HTML reports. It's designed to run identically on a Mac (via `uv`) and on an iPhone inside the **a-Shell** app (via plain `pip`/`python`), so it deliberately uses only pure-Python dependencies (no C/Rust extensions).

## Commands

```bash
# Install deps (uv-based project)
uv sync

# Run the full pipeline: parse xlsx -> translate/enrich foods -> analyze -> report
make analyze FILE=data/MacroFactor-Export.xlsx
# equivalent to:
PYTHONPATH=src uv run python -m omni_pilot.cli analyze "data/MacroFactor-Export.xlsx" --html

# Download the data files and missing MacroFactor exports from S3 / upload the changed data files
make pull    # cli pull --exports
make push    # cli push; `push --export FILE` uploads an export first

# Run tests
make test
# or
uv run pytest

# Run a single test file / test
uv run pytest tests/test_analyzer.py
uv run pytest tests/test_analyzer.py::test_name -v

# AWS stack tests (CDK; the infra dependency group is not installed by plain `uv sync`)
uv run --group infra pytest infra/tests

# Preview / deploy the AWS stack (bucket + app IAM user)
make infra-diff
make infra-deploy

# Regenerate requirements.txt (used for the iOS a-Shell / pip install path)
uv pip compile pyproject.toml -o requirements.txt
```

Config files must be created from templates before first run (`config/settings.yaml`, `config/supplements.yaml`, `config/food_mappings.yaml` from their `*.example.yaml` counterparts). `config/custom_foods.yaml` is optional (template: `config/custom_foods.example.yaml`); like the other personal config files it is gitignored and excluded from `make sync-iphone`. `config/settings.yaml` requires a USDA FoodData Central API key; a Gemini API key is optional but enables automatic food translation.

The personal data (`food_db.json`, `food_mappings.yaml`, `custom_foods.yaml` and every analysed MacroFactor export) lives in the S3 bucket `omni-pilot-data` (`eu-central-1`), so the Mac, the iPhone and cloud routines share one copy; iCloud only carries the code to the iPhone (`make sync-iphone`). The connection is the `s3` section of `settings.yaml` (`bucket`, `region`, `access_key_id`, `secret_access_key`). Each value can instead come from `OMNI_PILOT_S3_BUCKET`, `OMNI_PILOT_S3_REGION`, `OMNI_PILOT_S3_ACCESS_KEY_ID` or `OMNI_PILOT_S3_SECRET_ACCESS_KEY`, which win over `settings.yaml` (an empty variable counts as unset): a Claude cloud session is a fresh clone with a `settings.yaml` copied from the example, so the variables are how the custom-foods skill gets the key there. With none of the four set anywhere, the app works on local files only, as before S3; with some set and another missing, empty or still a `YOUR_…` placeholder, every command stops with exit code 1 naming the setting, never falling back to local files (that would split the data silently).

## Architecture

The CLI's main command (`analyze`, in [src/omni_pilot/cli.py](src/omni_pilot/cli.py)) runs a fixed autonomous pipeline through five modules in `src/omni_pilot/` (plus `matcher.py`, used by the enricher, and `custom_foods.py`). With S3 configured it pulls the data files first and saves to S3 after the report (see S3 storage below); `pull` and `push` are the same two steps as commands of their own, for the custom-foods skill, which edits files between them.

1. **`parser.py`** — Reads the "Food Log" sheet of a MacroFactor `.xlsx` export (fixed 0-indexed column layout) into `FoodEntry` records, and extracts the set of unique food names. Besides the macros it reads one micronutrient column, `Fiber (g)` (`fiber_g`, `None` for an empty cell), which the analyzer prefers over USDA's figure. `parse_daily_expenditure` reads each day's Expenditure (MacroFactor's TDEE; Target Calories as fallback) from the "Quick Export" sheet, and `check_last_day` flags the export's last day as partial when its logged calories (every entry, Quick Add included) are under half that figure; `cmd_analyze` then drops that day's entries before anything else runs and passes the check to `analyze` as `left_out_day`, which keeps it in `period.left_out_day` (BAR-87).
2. **`translator.py`** — Resolves each unique food name to a USDA-searchable English query string. Mapping precedence: TinyDB cache > `config/food_mappings.yaml` > Gemini API translation for anything still unresolved (via `resolve_and_sync_mappings`). Foods explicitly mapped to `"skip"` (e.g. water, "Quick Add", supplement pills) are excluded from analysis. Gemini calls go through the REST API directly (not an SDK) with a structured JSON schema response and `tenacity` retries. Besides the mappings it returns the foods Gemini was asked about but gave no translation for (an error or timeout, a wrong number of answers, an empty or `"ERROR"` answer); without a Gemini key that set is empty and an unmapped food's own name is its USDA query.
3. **`enricher.py`** — Looks up each mapped food name in USDA FoodData Central (SR Legacy / Foundation datasets), extracting a fixed set of nutrients (`USDA_NUTRIENT_MAP`: vitamins, minerals, omega-3s, amino acids) per 100g. It never trusts USDA's first search hit: `get_food_candidates` collects up to 25 hits for the query plus hits for its head words alone, and `matcher.pick_best` chooses among them (see `matcher.py` below). Queries are passed through `clean_query` first, because USDA's search returns HTTP 400 for `/` and, intermittently, for brackets. Results are cached in TinyDB (`db/food_db.json`) keyed by original food name + the USDA query used, so a changed mapping invalidates and refetches the cache entry. `enrich_all_foods` returns an `EnrichmentResult` with these parts: `profiles` (resolved foods only, never `None`), `skipped` (mapped to `"skip"`), `not_in_usda` (the USDA search ran and found nothing — needs a custom recipe, since a `food_mappings.yaml` edit is overridden by the DB translation), `lookup_failed` (USDA could not be asked, or a recipe ingredient could not be fetched — retried next run), `untranslated` (Gemini gave no translation this run — not searched in USDA and nothing cached, retried next run) and `low_confidence` (resolved foods whose match fits the logged macros poorly — still in `profiles` and counted, but named in the report). Keep `skipped`, `not_in_usda`, `lookup_failed` and `untranslated` distinct — the report labels them differently, and encoding them alike once made failed lookups read as deliberate skips, later network failures read as missing foods, and a Gemini timeout read as "give it a custom recipe" (a German name searched as is finds nothing, or a wrong food). Foods listed in a custom recipe (see `custom_foods.py`) bypass this path entirely: each recipe ingredient is fetched by FDC ID (`fetch_usda_food`, abridged `/food/{id}` endpoint), cached forever in the `usda_foods` table, and the food lands in `EnrichmentResult.custom` with its parts and a per-food `macro_distance` — never in `profiles` or `low_confidence`.
   - **`matcher.py`** — Pure functions (no I/O) that pick the USDA candidate matching what was eaten. `logged_macros_per_100g` turns MacroFactor's logged kcal/protein/fat/carbs into per-100g figures per food. `pick_best` keeps only candidates that *are* the named food (head-word filter on the start of the USDA description, so "Lebanon bologna, beef" never matches `beef, …`), then scores each by macro distance plus a penalty for missing query words — food identity first (feta beats camembert even with worse macros), macros deciding the form (raw vs cooked). Matches with macro distance above `GOOD_DISTANCE` are `weak`, and a pick is also `weak` when no candidate passes the head filter at all. Two other confidence values exist outside `pick_best`'s normal scoring: `no_macros` (the food has no logged grams to compare against) and `unverified` (a legacy cache entry kept as-is after a re-pick attempt failed). The thresholds were tuned by simulating against the production DB (spec: `docs/specs/2026-09-23-usda-candidate-matching-design.md`); re-run such a simulation before changing them.
   - **`custom_foods.py`** — Loads and validates the human-owned `custom_foods.yaml`: recipes of USDA ingredients (FDC ID + relative amount, scaled to shares) and the logged food names each recipe stands for. Invalid files raise `CustomFoodsError`, which stops the CLI. `recipe_macros` gives a recipe's share-weighted macros for the macro check. The CLI keeps recipe foods out of `resolve_and_sync_mappings`, so Gemini never translates them.
4. **`analyzer.py`** — Scales each food entry's per-100g nutrient values by actual serving weight, sums per day, averages across the date range, adds any configured supplement contributions, and compares against `config/reference_ranges.yaml` targets (RDA / AI / WHO per-kg-bodyweight amino acid targets, computed in `config.get_nutrient_target`). Some reference nutrients are sums of multiple USDA-tracked values (`COMBINED_NUTRIENTS`, e.g. methionine+cysteine, EPA+DHA). Status per nutrient is one of `ok` / `low` / `deficient` / `high` based on target and upper limit (UL). It also tracks **USDA data coverage** per nutrient: a food whose USDA profile has no value for a nutrient (`None`, meaning never assayed — distinct from a measured `0.0`) contributes nothing to that nutrient, and its serving weight is booked as unmeasured rather than zero-filled. A `not_in_usda`, `lookup_failed` or `untranslated` food is unmeasured for every nutrient, but only on a day that has a resolved food (a day with none is left out of the average entirely); without this, a partly unresolved day counted as a full day while reading as 100% coverage. `skip`-mapped foods stay out of coverage on both sides. Each nutrient carries `coverage_pct` (share of consumed weight that had a USDA value, `None` when no weight was attributable at all) and `is_floor` (a `low`/`deficient` verdict below full coverage, marked `*` in both reports because absent data can only push the true value up). A custom food is counted part by part (one part per recipe ingredient, weighing its share of the entry), so an ingredient missing a nutrient costs only its own share of coverage; `coverage.custom_recipes` lists the recipes used, their ingredients and each food's grams and macro check. Fiber is the one nutrient not always taken from USDA: an analysed entry whose logged MacroFactor fiber is above zero counts that figure as it is (it is per entry, so it is not scaled by weight, and it replaces every part of a custom food) and books the entry's whole weight as measured; `coverage.logged_fiber_pct` is the share of the fiber total that came from these logged figures.
5. **`reporter.py`** — Renders the `AnalysisResult` as a Rich terminal table (grouped by category: Vitamins, Minerals, Other, Amino Acids) and/or a self-contained HTML report via a Jinja2 template. When the last day was left out as partly logged, both report headers name it under the period line (yellow); when every day counted they say nothing about it. After the warnings for skipped foods, foods not in USDA ("give them a custom recipe"), failed lookups ("retried next run") and untranslated foods ("Gemini failed, retried next run"), the last three with their share of food weight (`coverage.not_in_usda_weight_pct` / `lookup_failed_weight_pct` / `untranslated_weight_pct`, skipped foods excluded), it prints a "Low-confidence matches" line naming weakly matched foods and their share of analysed weight (from `coverage.low_confidence_foods` / `low_confidence_weight_pct`, computed in `analyzer.py`). A Custom foods line (terminal) and section at the bottom of the HTML report show each recipe, its ingredients and the foods that used it, with `macros off N%` (⚠ above `GOOD_DISTANCE`). A dim "Fiber: N% from MacroFactor's logged values" line (a footnote in the HTML report) appears when any fiber came from the export. HTML reports are timestamped in `reports/` and also copied to `reports/latest.html`.

`config.py` centralizes YAML loading (`settings.yaml`, `reference_ranges.yaml`, `food_mappings.yaml`, `supplements.yaml`), path resolution (`resolve_path`, which expands `~`/env vars) and the S3 settings (`load_s3_config`: `None` when not configured, `S3ConfigError` when incomplete). `database_path`/`mappings_path`/`custom_foods_path` point at the device's local working copy of the data files; leave them at the repo defaults (`db/food_db.json`, `config/food_mappings.yaml`, `config/custom_foods.yaml`), since S3, not a shared folder, now keeps the devices in step.

### S3 storage

- **`s3.py`** — A minimal S3 client without an AWS SDK (`boto3` has C extensions and would not install in a-Shell): `get` (404 → `None`), conditional `put` (`if_match` / `if_none_match`) and `list` (ListObjectsV2, following continuation tokens), signed by hand with AWS Signature Version 4 in the `Authorization` header. Every failure is one `S3Error` with a `kind` (`network`, `auth`, `conflict`, `other`) and a message for the user; a 403 `RequestTimeTooSkewed` says the device clock is off rather than blaming the key. The signing is tested against AWS's published example values.
- **`sync.py`** — `pull` replaces the local data files with S3's and writes the sync state (`.s3_state.json` beside the database: each file's ETag and SHA-256 as downloaded, per device, never uploaded); `push` uploads the files whose SHA-256 changed since then, in the order `food_db.json`, `food_mappings.yaml`, `custom_foods.yaml`. `upload_export` stores a MacroFactor export as `exports/<first date>_<last date>_<hash8>.xlsx` (Food Log dates, file SHA-256), because the iPhone Shortcut always saves `data/data.xlsx` and the original name would overwrite earlier exports; the same file always gets the same key, so a re-upload answers "already in S3". `pull_exports` (`pull --exports`) downloads the exports missing from `data/`, where `recipe_tool.py` reads them; the custom-foods skill needs older exports for the macro check of foods eaten a while ago.

### Infrastructure

`infra/` holds the AWS CDK stack (`omni_pilot_infra/data_stack.py`, `OmniPilotDataStack`): the private versioned `omni-pilot-data` bucket and the `omni-pilot-app` IAM user. The user's policy grants only `s3:ListBucket`, `s3:GetObject` and `s3:PutObject` on that bucket and never delete; the stack creates no access key, which the user makes in the AWS console so the secret stays out of CloudFormation. Old object versions expire 30 days after they are replaced, which is the undo for a bad push. CDK is a separate `infra` dependency group, so it stays out of `requirements.txt` and the iPhone copy (`make sync-iphone` excludes `infra/`). AWS changes only with the user's go-ahead: show `make infra-diff` and wait before `make infra-deploy`.

### Data flow

```
S3 → sync.pull → local working copy (food_db.json, food_mappings.yaml, custom_foods.yaml)
xlsx → parser.parse_food_log → entries
entries, parser.parse_daily_expenditure → parser.check_last_day → entries without a partly logged last day
entries → parser.extract_unique_foods → food_names
custom_foods.yaml → custom_foods.load_custom_foods → custom_foods
food_names minus custom foods → translator.resolve_and_sync_mappings (TinyDB + YAML + Gemini) → mappings, untranslated
entries → matcher.logged_macros_per_100g → logged_macros
food_names, mappings, untranslated, logged_macros, custom_foods → enricher.enrich_all_foods (TinyDB cache + USDA API + matcher) → EnrichmentResult
entries, EnrichmentResult, ref_ranges, supplements → analyzer.analyze → AnalysisResult
AnalysisResult → reporter.print_terminal_report / generate_html_report
xlsx, changed data files → sync.upload_export, sync.push → S3
```

### Key invariants

- Nutrient keys are the single vocabulary tying `reference_ranges.yaml`, `USDA_NUTRIENT_MAP` in `enricher.py`, `COMBINED_NUTRIENTS` in `analyzer.py`, and `NUTRIENT_CATEGORIES` in `reporter.py` together — adding a new nutrient means touching all four.
- A reference nutrient key with no `USDA_NUTRIENT_MAP` entry surfaces as 0% coverage, not as a measured `0.0` — the coverage figure is what makes such a gap visible, so never reintroduce a `.get(key, 0.0)` default in the analyzer's summing or averaging steps.
- `omega3_epa_mg`/`omega3_dha_mg` are stored in grams by USDA but converted to mg during analysis (`analyzer.py`); watch for this unit mismatch when touching nutrient math.
- A USDA cache entry is reused when its `usda_query` matches and its `match_version` is equal to or newer than the current `MATCH_VERSION`; it's outdated (re-picked) when older or missing. This "equal or newer" rule (`enricher._is_current`) means a lagging device never re-picks an entry a newer device already stamped. Bump `MATCH_VERSION` in `enricher.py` whenever the candidate-picking logic changes in a way that should re-pick cached foods — the next `analyze` then re-matches every cached food once. A failed re-pick keeps the old entry (unstamped, retried next run) rather than deleting it, and entries are written with `upsert` so a food never has two cache entries. A pick made while one of the two USDA searches failed (rather than simply finding nothing) is also cached unstamped and retried next run, since it was chosen from an incomplete candidate set.
- A USDA search that ran and found nothing is cached as a not-found record in the same table (`not_found: True`, `usda_query`, `match_version`, `last_updated`, no `per_100g`) and answered from the cache for `NOT_FOUND_TTL_DAYS` (30); after that, after a `MATCH_VERSION` bump or after a mapping change, the food is searched again. A failed request (network error, timeout, any 4xx/5xx) is never cached — `get_food_candidates` reports it as an incomplete set — so the food is retried next run. A match written over a not-found record removes it first, because `upsert` merges fields. Older code reading a not-found record stops with `KeyError: 'per_100g'`; run current code.
- The custom-foods skill stores `reviewed_fdc_id` on entries of the main USDA cache table: the USDA ID it read beside the food's name and judged to be the same food (approved while it equals `usda_fdc_id`). The app never reads the field. A re-pick with an unchanged lookup text must keep merging into the existing entry (`upsert`), because replacing the entry would silently drop every review mark (`test_repick_keeps_fields_the_app_does_not_write`). A changed lookup text removes the entry, and with it the mark, on purpose.
- `cmd_analyze` stops with exit code 1 and writes no report (terminal or HTML) when no food resolved and at least one lookup failed or food went untranslated (BAR-43): a rejected USDA key on an empty cache, or Gemini down on a first run, would otherwise render every nutrient as deficient and overwrite `reports/latest.html`. A partial failure still reports, since the report labels it with its share of food weight; so does a run where nothing resolved because USDA has none of the foods.
- TinyDB (`db/food_db.json`) holds both food translations (`translations` table, written by `translator.py`) and USDA nutrient profiles (default table keyed by food name, and `usda_foods` keyed by FDC ID, both written by `enricher.py`); `config/food_mappings.yaml` is a human-editable mirror of the translations that gets synced both ways. With S3 configured, S3 holds the shared copy of all three files and these are the device's local working copy: a hand edit of `food_mappings.yaml` or `custom_foods.yaml` means pull, edit, push, because the next pull overwrites an unpushed edit.
- Pull: S3 always wins. It replaces the local files without checking for unpushed changes, deletes a local file S3 no longer has only when the sync state recorded an ETag for it (it came from S3; a file never in S3 is kept and recorded as absent, so the next push uploads it as new), and stops before touching anything when S3 has none of the three (wrong bucket). Files are written to a temp file and renamed, so a failure mid-write keeps the old file.
- Push: every data file goes up with a conditional `PUT` (`If-Match` with the ETag recorded at pull, sent exactly as S3 returned it, quotes included; `If-None-Match: *` when it was absent), so a file another device or the daily routine wrote meanwhile is refused (412) instead of overwritten. The first failure stops everything after it, and there is no merge: after `analyze` the user runs it again (it pulls first); after `push` the message says to `make pull` (which replaces the local changes), redo them and push again. Exports go up before the data files (`analyze` and `push --export`), so the database in S3 never names foods whose logged macros are missing from S3. A file deleted locally after a pull stops the push: the app user cannot delete in S3. No state file means every file is pushed as new (`If-None-Match: *`, so nothing in S3 is overwritten), which is how the one-time copy to S3 works.
- `analyze` with S3 configured pulls (no exports) right after the USDA key check; a failed pull exits 1 before anything else runs and writes no report. After the reports (terminal and HTML) it uploads the analysed export, then pushes. A failed upload prints `Results were not saved to S3: … Run analyze again.` in red and exits 1, keeping the reports, which are correct for the run; the next run's pull drops its local changes and the lookups are done again. The BAR-43 stop exits before any upload. Reports stay local and are never uploaded.
- Only the export's last day is checked for being partly logged, and only when there are at least two days: an earlier low day is real intake (or a day not logged) and stays in. A last day with no expenditure figure counts as a full day, with a printed note. Logged calories come from the Food Log sheet, not Quick Export's Calories column, which can lag behind it.
- Only a logged fiber value above zero is trusted. MacroFactor's export uses both an empty cell and `0.0` for "no value" as well as for a real zero (eggs have an empty fiber cell, one watermelon record a wrong `0.0`), so both fall back to USDA. The choice is made per logged entry, not per food name: the same name can point to different MacroFactor records. `skip`-mapped, `not_in_usda`, `lookup_failed` and `untranslated` foods ignore their logged fiber. Sodium was compared too and deliberately left on USDA (BAR-86).
- A custom recipe takes precedence over any mapping for its foods, including `skip`. Custom foods are never in `EnrichmentResult.profiles`: the analyzer counts them part by part, which is what keeps a missing nutrient in one ingredient from zero-filling or hiding the others.
- HTTP calls pass a `(connect, read)` timeout tuple with a short connect timeout (`GEMINI_TIMEOUT`, `USDA_TIMEOUT`, `S3_TIMEOUT`): the connect timeout applies to each address a host resolves to, tried in turn (Gemini's host has 16), so a single `timeout=30` once left the iPhone hanging for minutes on a network that drops IPv6. Gemini never retries a connection failure. `cli.main` also calls `net.prefer_ipv4_connections()`, which makes urllib3 try a host's IPv4 addresses before IPv6: iOS lists IPv6 first, and on a network that drops IPv6 each connection otherwise waits out the connect timeout on every IPv6 address (40s for Gemini's eight). IPv6 stays as the fallback, so IPv6-only networks still work. API keys go in request headers (`x-goog-api-key`, `X-Api-Key`), never the URL, because requests puts the URL into error messages that get logged. For the same reason S3 requests carry their SigV4 signature in the `Authorization` header and presigned URLs are never used; S3 errors name the setting or variable a key came from, never its value, and S3 requests are never retried, so "not saved" stays unambiguous.
- The `usda_foods` table (custom-food ingredients) is keyed by `fdc_id` and never invalidated — an FDC ID always names the same food. A failed ingredient fetch caches nothing and makes every food of that recipe `lookup_failed` for the run.
